Inspect the experiment status before using its measurements. Preserve failed runs as evidence rather than silently treating missing metrics as zero.

<Anchor id="load-saved-evidence" />

## Load saved evidence

```python
from pathlib import Path
import cloudai.api

system = Path("standalone.toml")
experiment = cloudai.api.get_experiment(Path("results/your-experiment-directory"), system)
print(experiment.status)
```

Use the system config from execution and a result directory directly under its `output_path`.
Use `list_experiments(system)` to discover saved experiments.
See [Read results and generate reports](/reporting) for the record structure and [Python API](/api) for lookup errors.

<Anchor id="distinguish-failures" />

## Distinguish failures

Configuration and setup errors raise exceptions. Workload failures appear in the returned experiment's status.
A job submission failure can raise `SystemExit(1)`; handle it separately when embedding CloudAI in a long-lived application.
Missing metrics need investigation even when a process completed. Store logs and the generated configuration so
another process or person can diagnose the cause.

<Anchor id="cancellation" />

## Cancellation

Pass `on_start` to receive the initial experiment and cancellation function before execution begins.
The call remains synchronous; the callback is not an asynchronous execution API. Follow the contract in [Python API](/api)
when integrating with an application's cancellation handling.
